## 结论与范围

管理员在 2026-10-20（本机时区）授权把 GitHub 搜索失败交给 bot 的独立开发执行器。通过本机维护 CLI 提交到现有 dev-worker，由 DSH 在独立副本修改源码，worker 独立复测；维护者审查后在本地 MaiBot 分支保存候选。

历史回复中的“操作过于频繁”来自宿主工具限流，不能据此认定 GitHub 返回了 403/429。当前基线已经支持冷却后续跑，本轮确定性回归未复现旧的直接中断行为；实际补齐的是失败原因、未执行状态和阶段结果的交付。

最终源码候选已提交，**尚未部署、未重启服务、未进行真实 GitHub 或 QQ 验收**。本机 CLI 任务不绑定群消息来源，所以不会向 QQ 自动发完成通知；这次验收覆盖执行器和独立测试，不覆盖群内自动提交入口。

## 最终改动

- `runtime.py`：本地冷却且等待预算不足时，明确说明本次调用未执行、没有发出远端请求，并保留机器可读状态；向证据收集器传入调用目标。
- `search_evidence.py`：区分失败与未执行，阶段回复保留工具返回的原因；优先安排已有来源和摘录，再用剩余字数给出失败说明，超长时明确省略。
- 相关测试：跨任务及跨会话同用户共享配额、只执行待执行调用、冷却中取消、预算不足仍交付来源、上游失败不伪装成零结果，以及长错误、小预算、长链接等边界。

审查复现：一次成功搜索后追加六条长错误，首轮候选的 1500 字回复丢失了成功 URL 和正文；修订后回复为 1499 字，保留完整成功 URL、正文及有界失败说明。维护者独立运行该复现确认修复。

配额未调整：每用户每工具 2 次 / 60 秒，每任务最多 20 轮工具调用、总等待 240 秒。

## 尚不能得出的结论

工作副本目前只克隆 MaiBot Git 仓库。独立的 `plugins/qqbot-web-search` 仓库没有进入本次开发副本；当前工具是 DuckDuckGo/Bing 的 `web_search` 和 `read_webpage`，没有专门的 GitHub API 工具。因此本轮不能证明或修复真实 GitHub 的访问限制，也没有验证插件对实际 403/429、普通无结果的映射。

生产工作流发布状态、QQ 登录和其他未提交修改未被本轮任务改动。若继续处理插件内部问题，需要把对应独立仓库纳入开发任务，并提供实际请求目标及脱敏错误证据。
