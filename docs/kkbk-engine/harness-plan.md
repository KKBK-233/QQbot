# DeepSeek Harness 与任务工作流实现计划

更新日期：2026-10-21（UTC-7）。本文保留稳定设计；当前部署与验收见 [状态表](status.md)，历次交付证据见 [CHANGELOG](CHANGELOG.md)。

## 目标与架构

MaiBot 保留收发消息、数据库、模型服务、记忆和现有插件。日常层负责聊天和分流，任务层负责工具与工作流执行。独立 DeepSeek Harness 在收到管理员教学、开发需求或真实瓶颈时，组织开发任务，通过真正的开发代理修改完整项目工作副本，验证后发布回运行系统。

```text
QQ / SnowLuma → MaiBot 基础设施
                 ├─ 日常层：聊天、关注、任务分流
                 └─ 任务层：工具 + 版本化工作流
                            │ 教学 / 故障 / 能力缺口
                            ▼
                   DeepSeek Harness 开发协调层
                            │
                   独立开发服务：代理、Shell、Git、测试
                            │
                   验证与发布 → 更新前两层及必要基础设施
                            └─ 失败恢复
```

开发能力不受插件接口限制，可修改引擎、工具、模型适配、启动脚本等源码。完整工作副本与运行目录分离。记忆模块不重新设计；开发账本只负责状态与证据。权限来自宿主实际身份，不能由聊天文本、记忆或模型参数授予。2026-10-19 在下一阶段前进行功能精简，离线 Python 沙箱已按用户决定下架，其余候选项见 feature-inventory.md，未经选择不调整。

## 阶段与验收

| 阶段 | 实现内容 | 验收标准 |
| --- | --- | --- |
| 1 工作流基础 | 文件格式、启用清单、加载验证、每任务不可变快照、任务层接入、版本记录、搜索示例 | 文件更新只影响后续任务；补试沿用同一版本；坏配置可诊断；轻层不携带完整流程、不新增模型调用 |
| 2 开发执行入口 | 独立开发服务、完整代码工作副本、开发代理适配、Shell/Git/依赖/测试、进程回收 | 管理员提交开发需求后得到可检查补丁和测试结果；不修改运行目录；取消能停止任务子进程 |
| 3 教学与任务协调 | 持久任务账本、实际身份校验、教学作用范围、验收条件、进度和取消、开发任务恢复 | “这次这样做”只影响当前任务；“以后这类任务这样做”形成工作流候选更新；重启不丢状态、不重复交付 |
| 4 验证与发布 | 绑定源码版本的测试、集成环境、串行部署、健康检查、业务验收、上一版本恢复 | 故障候选不会持续影响运行服务；恢复演练通过；数据库迁移单独验证 |
| 5 主动改进 | 从真实失败与重复操作生成改进需求、去重、收益排序、实验、经验写回 | 自主解决一个真实瓶颈，并在独立任务中复现改善；未验证假设不当作有效经验 |
| 6 长期运行 | 任务/版本/用量可见、暂停自主开发、故障演练、认证异常处理、管理页面 | 无无限失败重试；认证失败、超时、进程退出、发布失败有可解释状态与恢复路径 |

各阶段按依赖顺序推进。阶段 2 可以在阶段 1 验收后独立开发；阶段 3 将二者串成教学闭环。新身份在后续独立变更中实现，不混入第一步加载器。

## 教学更新闭环

示例：“以后这类搜索先查官方资料，找不到再查社区，结论要打开原文核实。”

1. 宿主核验实际请求者为管理员 `1020050112`，记录原始请求与作用范围。
2. 协调层形成目标、限制、验收样例；若只要求本次操作，不改持久流程。
3. 开发代理读取现行工作流与工具能力，修改工作副本，生成新版本。
4. 校验结构和工具引用，再使用独立样例验证行为；不得把仅有提示词的流程当作强制执行器。
5. 发布经过验收的版本；新任务使用新版，进行中任务保持原快照。
6. 对后续任务观察效果，将有证据的经验写入现有记忆，保留版本和失败记录。

## 复用与边界

- 复用 MaiBot ToolRegistry、模型服务、发送回执、插件加载/重载和现有记忆处理器。
- 旧离线 Python 已下架，不作为开发环境基础。后续开发服务独立接入 Shell、Git 与开发代理。
- 插件 API 能力校验不是系统隔离。开发环境单独提供资源与文件边界，不将生产凭据、QQ 登录目录和数据库随源码复制。
- 开发任务最初并发 1；同一部署目标串行发布。现有工具配额保留，不擅自增加全局每日费用上限。
- 开发执行需要单任务超时、轮数与无进展退出；精确账单不可得时报告可取得用量和未知部分。
- 代码恢复不意味着数据库或外部副作用已撤销；消息和图片交付记录回执，恢复时避免重复执行。
- 发布策略初期允许已批准范围内的扩展自动试运行；核心、权限和破坏性数据迁移采用单独确认。后续由用户调整自动上线范围。
- 用户原有未提交修改保留；关键节点提交精确文件。PR 与合并遵守既有授权要求。

## 首个端到端里程碑

后续开发约定已明确：DSH 的开发范围包括人设、提示词及整个项目，开发产物投入工作流层供对话层使用；bot 应能够补充需求、回答问题并继续同一 DSH 开发会话，不能只做一次性派发。开发需推进到约定验收，资源不足或缺少接线时保留明确阻塞及恢复点。开发提示与最小会话控制现已接入源码，完整能力发布仍待实施，具体边界见 [DSH 开发约定与持续会话设计](dsh-development-contract.md)。

管理员进行一次搜索教学 → 开发代理修改搜索流程 → 独立样例验证 → 发布候选版本 → 下一次真实任务按新流程执行。最终证据包括教学来源、旧新版本、补丁、测试、发布记录和真实任务结果。

这证明系统能把教学固化为执行改进。模型权重训练不在本计划内；持续成长依靠流程、源码、工具和有效经验的积累。
